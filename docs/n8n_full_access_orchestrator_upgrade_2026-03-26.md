# Full-access orchestrator upgrade

_Дата: 2026-03-26 UTC_

## Кратко

В основной workflow `Telegram Coach - Main` внедрён новый оркестраторный слой, который может самостоятельно читать и писать файлы внутри `/obsidian` в зависимости от ситуации. Это шаг от жёстко прошитой логики к agentic orchestration-подходу, где модель сначала оценивает, хватает ли ей текущего lite-context, а затем при необходимости обращается к vault.

## Что изменилось

### 1. Оркестратор с full-access к Obsidian vault

Реализован orchestration-узел, который работает внутри main workflow и даёт модели возможность:

- читать заметки и другие файлы в vault при нехватке контекста;
- искать релевантные записи перед ответом пользователю;
- записывать важное знание пользователя в Obsidian;
- создавать заметки по прямой просьбе пользователя;
- подготавливать действия для reminder / scheduling логики.

Full access здесь означает полный read/write доступ **внутри `/obsidian`**. Доступ ко всей файловой системе сервера сознательно не открывался.

### 2. Обновлённый экспорт main workflow

Сохранён экспорт workflow после патча:

- `workflows/main/main_KJBp4f0aPCZWAsjV_after_full_access_orchestrator.json`

Этот экспорт можно использовать как точку восстановления и как артефакт для code review.

### 3. Живые smoke-tests

Проводились live тесты через webhook с инструкцией записать строку в файл:

- `/obsidian/Ideas/full-access-test.md`

Тесты подтвердили, что workflow стартует, а оркестратор действительно исполняется в рантайме.

## Найденные проблемы

### Исправлено

- ошибка в оркестраторе `URL is not defined`.

### Ещё остаётся

- после исправления orchestration-ошибки execution доходит до `Send Reply`, где падает с ошибкой:
  - `Bad request - please check your parameters`

Это означает, что слой оркестрации уже встроен, но финальный end-to-end сценарий `получить сообщение -> прочитать/записать vault -> ответить в Telegram` ещё требует доводки.

## Текущее архитектурное значение апгрейда

Новая схема приближает систему к следующей модели:

1. `Telegram ingress`
2. `normalize text / voice`
3. `lite context`
4. `orchestrator`
5. `optional vault read/write`
6. `final reply / schedule`

То есть LLM больше не ограничен только тем контекстом, который заранее собран в `Read Notes`, а может идти за дополнительной информацией в Obsidian при реальной необходимости.

## Зачем это важно

Этот шаг делает систему гораздо более гибкой:

- меньше хардкода под конкретные сценарии;
- больше шансов корректно понять, о чём говорит пользователь;
- появляется основа для сохранения долгосрочных знаний в vault;
- можно постепенно перейти к настоящему tool-using orchestration и подграфам.
